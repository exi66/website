**Стек:** Java 8, Maven, Mixin, ASM, Javassist, Swing (FlatLaf), JUnit, GitHub Actions

## Задача

У клиента игры нет API для модов, а его код обфусцирован, и имена классов меняются с каждым обновлением. Из-за этого любая доработка ломалась при выходе новой версии, и её приходилось переписывать почти с нуля. Нужна была инфраструктура, на которой моды переживают обновления игры.

## Решение

Maven-проект из 12 модулей, около 16 тысяч строк собственного кода на Java. Основные части:

- **Конвейер деобфускации.** Снимает обфускацию и шифрование строк и даёт всем классам и методам стабильные номерные имена, по аналогии с intermediary у Fabric. Поверх этого лежит карта человекочитаемых имён в формате Tiny v2.
- **Перенос карты имён между версиями игры.** При обновлении совпадения классов находятся автоматически, и карта переносится с прошлого релиза. Обновление сведено к двум командам Maven, а код модов остаётся прежним.
- **От Javassist к Mixin.** Долгое время изменения в клиент вносились через Javassist. В 2026 году я перевёл платформу на Mixin и Maven-монорепозиторий, сохранив все функции модов.
- **Загрузчик модов.** Моды внедряются в байткод клиента через Mixin и описываются манифестом с зависимостями между модами, по аналогии с Fabric. Поверх загрузчика есть API событий, чтобы простым модам не нужны были mixin'ы.
- **Моды на этой платформе:** библиотека окон со своей темой и компонентами, рисование на игровых холстах, превью построек из файлов `.schematic`, исправления ошибок самой игры и LWJGL.
- **Headless-клиент.** Вход в игру и чат без окна и OpenGL.
- **Тестовый сервер.** Плоский мир и вход без авторизации, чтобы проверять моды локально.

## Качество

Тесты запускают настоящий загрузчик против актуального jar игры, без окна и нативных библиотек, поэтому работают в CI. Они проверяют, что все mixin'ы применяются, каждая цель изменена и байткод проходит верификатор JVM. Отдельный тест следит, чтобы окна модов не зашивали цвета в обход темы. По тегу GitHub Actions собирает клиент и публикует релиз.
